# 统一开发、交付与验证标准

[Notion 正文](https://app.notion.com/p/420572fed03281b0b552f7474cc3ec7d?pvs=204)

**当前修订为 V1.2。** 适用于装点猫管理后台 `HlloUJ/zdm`。本页沿用统一标准的原地址，以后直接在这里更新。

**执行版本。** 以目标主线 `main` 的 `dev/quality/release.mjs` 为准。开关为 `false` 时仍按 V1.1 验证。006 的启用提交将开关切到 `true` 后，V1.2 生效，新任务在开工时初判，在途任务按真实时点接入，开发后按实际差异复核。生效提交、时间与验收结果登记在同一份 [Notion 标准](https://app.notion.com/p/420572fed03281b0b552f7474cc3ec7d?pvs=204)。

## 一、一个任务从交办到交付怎么走

1. **开工前先读需求。** 执行者查清这次要改变什么、谁会受影响、出错有什么后果，给出初判和验证重点。在对应任务对话告诉用户“判了几级、为什么”，再开始实质实施。
2. **开发中随事实调整。** 需求补充、方案更新或查到新的使用方时，重新判断。升档、降档都要及时在该任务对话解释。
3. **开发后看实际改动。** 对照原要求，检查做了什么、漏了什么、影响到谁，确定本轮等级和该跑的检查。验证通过后按已有流程提交验收。
4. **交付前看整个任务。** 用目标主线和完整交付候选重新核对累计影响。已经测过且仍然适用的结果可以复用，余下的检查必须补齐。合并后核对实际运行版本并完成交接。

本标准覆盖用户直接交办、总协调派发、同批多任务、跨对话接手，以及独立交办的文档、测试、工程和业务任务。任务执行者负责定级和告知，用户照常交办和验收。总协调负责把原始要求、验收条件和文档入口交给执行者。任务已有授权决定可以做什么，等级决定该怎么验证。实现难度和依赖用来安排工期与分步方式。例如一行权限判断可能很快写完，仍需要严格验证。

原来 001 的两个显示文字因为落在共享服务文件里被算成 R3，加入配套测试后整项又被推到 R4。V1.2 把判断提前到开工前，开发后再沿实际使用方核实，等级和选测一起调整。[当时的差异判级规则](https://github.com/HlloUJ/zdm/blob/43860ed334545f14135969f9e2d93ed81555c5cc/dev/quality/policy.mjs#L97) · [001 的实际改动](https://github.com/HlloUJ/zdm/pull/8/files)

## 二、开工前怎样判 R0–R4

以本次交办为起点，读取与它有关的有效 PRD、方案、验收条件和现有实现。写清改前与改后的真实行为、使用方或受影响的数据，以及判断依据。引用可定位到文档版本、条款、现有调用方或基线提交。简单任务一句话即可。遇到文档冲突先核对版本和适用范围。只有确实影响业务含义或授权且现有资料无法解释时，才请用户裁定。

| 等级 | 什么变化应判这一级 | 开发先验证什么 | 交付前必须覆盖什么 |
| --- | --- | --- | --- |
| R0 内容、纯文案 | 说明、注释，或能证明只换展示措辞，业务含义、稳定标识和程序行为都相同 | 核对内容、引用和差异。运行时文案核对实际出现的位置 | 文档与行为相符。受影响的标签、列表、详情或人读日志显示正确 |
| R1 局部展示或交互 | 一个页面或组件调整布局、展示方式、沿用现有能力的简单操作 | 直接受影响的组件、操作和状态 | 相关交互与状态。布局变化覆盖受影响视口 |
| R2 局部业务功能 | 边界明确的表单、筛选、查询或单模块普通流程 | 相关逻辑和关键流程 | 正常、边界和失败路径 |
| R3 共享或跨模块改动 | 多个真实使用方依赖的接口、事件、共享规则、路由或构建约定发生变化 | 改动本身、共享契约和已知调用方 | 在 R2 基础上覆盖真实使用方、兼容性和跨模块组合 |
| R4 高风险改动 | 登录授权、数据隔离、价格库存、迁移删除、验证器或交付放行等高风险行为实际改变 | 最容易造成严重后果的路径，如错误授权、误删或错误放行 | 完整覆盖受影响的前后端、数据或交付链路，以及对应的专项检查 |

逐项判断行为，整项取最高等级，验证计划合并各项确有依据的检查。共享文件、测试目录、关键词、行数和工时都是排查线索。进入共享服务文件要看改变的是一段人读文字还是多个调用方依赖的行为。跟着文案改测试期望或补翻页用例，计入该行为的验证。删除关键越权断言、跳过隔离检查或改变放行条件，须单独评估被削弱的保护。写入工作流的 Markdown 指令按其执行后果判断。

**R0 与 R1 的分界。** 同一个入库动作只改标签和人读日志，核对文字没有参与程序判断、筛选、审计标识或外部契约，可以判 R0。若改了分页选项或点击后的展示方式，即使后台接口照旧，用户能做的操作已经变化，属于 R1。若永久删除的提示变成“移入回收站”，先核对危险操作的后果和用户会如何理解，不能按纯文案放行。

开工时没有 Git 差异也能根据需求初判。拿不准时先做最小只读核查，仍缺事实就告诉用户暂定等级、未知点和复判条件。影响只定位到业务域时运行该域完整验证，范围完全不明时临时使用项目完整适用门禁。查清以后再收敛等级与选测范围。

## 三、用户在任务里会看到什么

| 时刻 | 对应任务对话中的消息 |
| --- | --- |
| 首次实际开工 | 任务全名、当前或暂定等级、一句事实依据、本轮验证重点。待办登记与实际开工分别记录 |
| 恢复工作、接手后开工、开始一轮返工 | 每次都发，即使等级沿用。说清本轮做什么、为什么沿用或调整。一次命令重试仍算同一轮 |
| 需求或实际改动导致升级、降级 | 发现时及时发“原等级 → 新等级”，点明改变判断的事实，以及增减哪些验证。交付 CI 发现的变化由跟进交付的执行者发回任务对话 |
| 开发后复核 | 把实际等级和依据写入本轮结果。等级变化同时主动告知。同一时点又开工又改级，一条消息写清两件事即可 |

本轮和整项相同时报一个等级。两者不同时分别说明，例如“003 整项仍是 R4，因为要验证同店并发和跨店隔离。本轮只修空清单背景，按 R1，核对背景是否铺满”。升档示例为“查到两个页面共用这次要改的分页事件，从 R2 升为 R3，两个页面都要验。”降档示例为“已核实事件和入参沿用原约定，只改本页展开和收起，从 R3 降为 R1，验证本页操作和状态。”

消息由承接任务的执行者发送。总协调同时承接多项工作时用各任务全名标识，有独立任务对话时在该对话发送。程序将判定和待发消息一并保存，以任务、真实开工轮次或判定修订号去重。发送后记录实际时间和可取得的消息引用。中断后先查目标对话，再按需补发并说明原判定时间。以用户在对应任务对话能看到消息为送达依据，命令输出、台账标记和 5274 的验收通知各有自己的用途。

## 四、开发、复核与交付怎样执行

| 节点 | 谁用什么依据检查 | 结果 |
| --- | --- | --- |
| 形成可测改动或完成一轮返工 | 执行者用 `verify:plan`、`verify:dev` 对照原需求和实际新增、修改、删除、未跟踪文件，核对使用方、数据与测试变化。本轮与上次相关验证通过的准确版本比较 | 留下初判、实改后的等级和原因。开发验证随可测改动触发，自动记录实跑的命令、用例范围、版本、环境和结果。文档任务复核实际文本及引用 |
| 业务版本送 5274 验收 | 适用开发检查通过后，在任务自己的工作区保存 checkpoint。`publish` 将任务、复核记录和开发证据绑定到实际发布的源码树，`verify` 核对运行版本与健康 | 成功后交用户验收。各待验收任务分别保有版本和判定，返工后的新版本同样核对 |
| 正式交付 | 业务任务收到用户对该任务的“任务完成”或对该批次的“今天工作完成”时，冻结实际任务工作区的完整业务快照，包含未完善内容。涉及 5274 时核对该任务的验收版本，从任务分支生成候选。已有交付授权的工程任务进入 PR 时触发 | 对照目标主线与完整候选的累积行为得出整项等级，合并所有必测项。多次 R1 返工也要核对组合后的影响 |
| 合并前 | 可靠 PR CI 对最终组合核验证据并补跑剩余项。CI 缺失、不可靠或覆盖不明时，通过 `verify:delivery` 回到本地完整适用交付门禁。远端已配置的必需检查仍须通过 | 必测项有失败或缺少有效结果，停在合并前，保存首次失败。候选或目标主线变更后重验受影响部分 |
| 合并后 | 核对 `main` 与验证候选的合并关系，补验发生变化的输入。同步本地主线和 5274，核对版本、健康、数据绑定及其他待验收任务 | 完成运行交接、释放任务锁，再按现行规则安全清理任务专属资源。分别记录合并、主线验证、运行交接和清理状态 |

复核先看原要求是否实现。要求库存回补，候选却只改了文字，应记录“库存回补尚未实现”。降档需要事实依据，例如原能力已经满足要求，或用户明确缩小范围。正式交付沿用完整业务快照规则，发现的业务缺口如实列为后续工作。每项选测都说明要防什么、实际跑哪些用例。把 005 标签改成 R1 却依然要求无关的全量后端检查，属于选测错误。[5274 验收流程](https://github.com/HlloUJ/zdm/blob/ad098f361c8f5e165625683168475b3ce5555543/README.md#L29) · [运行交接与清理](https://github.com/HlloUJ/zdm/blob/ad098f361c8f5e165625683168475b3ce5555543/docs/task-completion-cleanup.md#L3)

## 五、哪些必须测，哪些结果能复用

所有等级都检查交付差异。静态检查、类型检查、构建和项目守卫按实际影响纳入。命中以下行为时，选入对应专项。

| 行为 | 最低专项覆盖 |
| --- | --- |
| 异步、并发、重入 | 顺序变化、重复请求、竞争、失败恢复 |
| 状态流转 | 允许的转换、应被拒绝的转换、失败后的状态 |
| 权限、数据范围 | 允许、拒绝、跨用户或跨组织隔离 |
| 批量操作 | 部分失败、重复执行、结果一致性 |
| 接口契约 | 请求、响应、错误处理、现有调用方兼容 |
| 迁移、持久化 | 历史数据、约束、适用的升级路径 |
| 删除、资源回收 | 对象归属、引用保护、重复执行、中断接续 |
| 验证、交付控制 | 正常放行、应当拒绝、证据失效、恢复 |

按单项检查复用。程序要能从可信原始记录核对候选、目标主线、标准与计划版本、实际用例范围及相关输入。提交号变化后能证明相关输入等价，该项结果仍有效。

| 已有结果 | 复用条件 |
| --- | --- |
| 单测、组件测试、类型检查、构建 | 相关源码、测试、依赖、配置与工具环境等价。部分用例只能覆盖已跑部分 |
| 接口、跨模块、端到端 | 再核对真实使用方、前后端组合、数据和权限条件。共享契约变更时重验受影响的使用方 |
| 权限、迁移、数据一致性、失败恢复 | 再核对角色、数据库版本、迁移路径、数据基线或运行绑定。共享环境交接还要核对当次状态 |
| PR CI 用于主线 | 验证准确的主线、候选、合并父提交与源码树，核对相关输入、环境、实际报告和来源 |
| 聊天里说“测过了”、绿色状态或一次 HTTP 200 | 可以作线索。证明测试通过需有对应检查的原始结果，HTTP 200 只证明当时可访问 |

每项结果标明**本次执行通过、有效复用、不适用、执行失败、尚未完成**之一。“不适用”附可核验的范围依据。证据保存在临时工作区之外，清理后仍可追溯。结项记录列出标准版本、最终等级、影响范围、实跑与复用、实际执行和等待耗时，无法核实的耗时标明未知。

## 六、确认后，006 具体改哪里

| 位置 | 按本标准实现什么 |
| --- | --- |
| Notion 与仓库标准 | 本页统一规定判级、开发、验证、交付与启用，后续修订沿用同一地址。仓库发布时保存与确认版对应的 `docs` 版本并标明出处，供代码与 CI 定位。任务页、派发说明和 Skill 统一引用本页及其生效修订 |

| 任务登记和计时 `dev/task-timing.mjs` | 复用真实任务号或原交办引用、本机写锁。拟提供 `npm run task:assess -- start`、`review`、`show`，用于开工、复核和接手续查。待办、实际开工、等级修订、待发和实际送达各有记录。原 `notified` 专用于验收计时 |
| 差异分析和验证计划 `dev/quality/repository.mjs`、`policy.mjs` | 将任务语义与可独立检查的事实交给计划器。读取前后内容，定位稳定标识、显示用途、实际调用方、数据写入和放行规则。路径用于定位，配套测试归入它验证的行为。动态调用或无法证明的范围按第二节回退 |
| 开发与测试入口 | 把风险映射到实际命令、具体用例、相关输入与环境。接入现有 `npm run build`、`npm run test:unit`、`npm run backend:test`、`npm run test:ledger`、`npm run test:e2e` 和 5274 专项 `node --test tests/acceptance.test.mjs`。工具不能可靠选测时运行该工具支持的完整检查 |
| 5274、PR 和主线 | `dev/acceptance.mjs`、PR 工作流、`verify:merge` 和 `verify:main` 绑定真实任务、修订、候选以及实际合并树。将远端发现的改级结果传给执行对话。报告显示开工判断、每轮复核、最终结论及实际验证耗时 |

**本机记录。** 在 Git 公共目录按任务保存，以便换工作区或对话时接续。每次修订记录交办和有效文档引用、行为、使用方、关键未知点、等级和选测理由。复核增加基线、候选、规则版本、变化原因和通知状态。沿用写锁、前一修订号校验和一次完整落盘，同时保存判定和待发消息。不同任务分别记录和通知，同批候选合并实际需要的检查。旧工作区按仓库已发布的流程接入。

**CI 怎样独立核实。** 本机保存私有交办和文档定位。PR 的结构化摘要只传该仓可见的任务标识、行为、待核事实、检查、规则版本和基线候选。CI 可在没有本机台账、聊天和 Notion 会话时运行，依据目标主线已发布的规则和真实合并树独立复核。将摘要指纹、规则、主线、候选和合并树绑定到完整报告。摘要或代码变化就重算相关计划。缩小覆盖必须有 CI 可复核的事实，候选自报低等级或自改验证器不能获得豁免。报告须写明哪些保护是远端强制、哪些依赖本地流程。[已发布的验证入口](https://github.com/HlloUJ/zdm/blob/43860ed334545f14135969f9e2d93ed81555c5cc/dev/quality-entry.mjs#L21) · [PR 与主线的证据复用](https://github.com/HlloUJ/zdm/blob/43860ed334545f14135969f9e2d93ed81555c5cc/dev/quality/remote.mjs#L98)

## 七、006 怎样验收

以下是新版的验收预期。要同时核对**等级、理由、实际选中的检查**，涉及通知的场景还要看真实任务对话。以下四个任务用来校准通用判断，任务号、目录或测试文件名都不能成为判级条件。

| 场景 | 通过条件 |
| --- | --- |
| 001 只换入库标签和人读日志文字 | R0。核对两个展示位置和含义，加入同步期望文字的测试后，等级保持 R0，不附加无关全量后端检查。[001 原始改动](https://github.com/HlloUJ/zdm/pull/8/files) |
| 003 整项功能及其一轮空清单背景返工 | 整项 R4，覆盖同店两人同时选品和跨店数据隔离。孤立的背景返工 R1，验证布局。返工消息和整项交付报告各自说清范围 |
| 004 删除检查、重复提交与验证规则 | 整项 R4，具体覆盖误删、重复执行、错误放行与适用的恢复路径。[004 实际改动](https://github.com/HlloUJ/zdm/pull/10) |
| 005 款项配置分页 | R1。验证每页 10、20、50 条、翻页和所显示的记录。加入配套测试后等级保持 R1，无关全量后端检查不进入计划。[005 分页改动](https://github.com/HlloUJ/zdm/pull/9/files) |

## 八、审阅、实施与正式启用的顺序

1. **确认实施依据。** 本页包含等级、开发与交付、代码和 Skill 的分工、验收与启用安排。用户已确认本页 V1.2 作为 006 的实施依据。006 从保留的试验和本地提交接续，项目在正式启用前继续执行已发布规则。
2. **确认后再改。** 记录用户确认的准确文档版本。006 对照该版本核对已有试验，按“哪条要求 → 哪个代码或 Skill 入口负责 → 用什么场景验收”补缺、纠偏，已有符合的工作可复用。若实施发现必须改变已确认的判级口径、必测项或用户通知约定，先把差异反馈到本标准，待确认该修订后再据此改动。
3. **先比较，再切换。** 提前固定历史样本、预留样本和判级预期。接通开工、通知、复核到交付的链路后，在同一候选上比较新旧规则会选哪些检查，复用已有结果，避免重复跑两套完整门禁。试运行报告写明当前生效规则和拟议结果。
4. **以 R4 验收 006 并启用。** 006 改变验证和合并放行，使用目标主线已发布的规则及事先固定的验收条件检验第七节。记录验收结果、生效提交、标准修订号和启用时间，通知总协调与 006，并在任务中告知用户。直接更新本页的执行状态，后续任务在同一地址查生效规则。
5. **已在途的任务按真实时点接入。** 新任务和待办在实际开工时接入。进行中任务在下一次实质工作或复核时写“接入时评估”，旧任务沿用原交办引用、发号和计时口径，历史开工消息不补造。
6. **漏判或错误放行可以回退。** 切回上一套已发布策略或完整适用门禁，记录回退时间、受影响任务和当前依据，保留历次判定、消息和证据。若某任务等级随之改变，在本任务对话主动说明。修正后重放相关样本，通过再恢复。运行后按相近任务比较验证耗时、首次通过率、返工和误判原因，分别查清误升、误降和漏测发生在哪里。
