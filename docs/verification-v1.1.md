# 统一开发、交付与验证标准 V1.1

范围为本仓库的业务和工程任务。`dev/quality/policy.mjs` 定义 R0–R4、检查命令、影响范围和专项场景。开发、合并前及主线验证共用这份映射。`npm run verify:plan` 输出当前改动的判级依据、开发和交付清单。

| 等级 | 适用范围 | 最低覆盖 |
| --- | --- | --- |
| R0 | 纯说明 | 内容及差异 |
| R1 | 已登记的局部布局与交互 | 相关组件、操作状态与视口 |
| R2 | 局部业务功能 | 正常、边界及失败流程 |
| R3 | 共享组件、服务或跨模块契约 | 相关功能、契约及使用方 |
| R4 | 权限、隔离、重要数据、迁移、删除或验证及交付控制 | 受影响的完整链路和对应专项 |

多类改动取最高等级与检查并集。新增、删除、未暂存和未跟踪源码都参与开发计划。已登记且隔离清楚的改动采用定向检查，无法确定影响范围时运行项目完整门禁。计划的 `specialties` 列出并发、状态流转、权限、批量操作、接口、迁移、清理和验证控制等命中的最低场景。实现新增行为时同步补足相应测试。

## 开发与验收

形成可测试的改动或完成返工时运行 `npm run verify:dev`。原有 `npm run build`、`test:unit`、`test:e2e`、`backend:test` 和 `test:ledger` 仍执行原生工具，并在 Git 工作目录内记录命令及实际范围。附加过滤条件的结果只覆盖相应范围。业务 checkpoint 通过现有 5274 `publish` 入口发布，入口先按开发清单核对证据。5274 `verify` 核对验收版本与实际运行状态。

## 交付

业务任务收到正式交付指令时先冻结实际工作区。工程任务进入正式 PR 流程时同样执行合并前门禁。可靠 PR CI 针对实际合并组合运行 `delivery`。需要本地回退时，先同步 `origin/main`，在包含该主线的干净任务候选上完成 `npm run verify:delivery`，可用 `npm run verify:assert-delivery` 核验凭据。缺少或失效的适用项须补齐。已配置的远端必需检查仍须通过。

从任务分支执行 `npm run verify:merge -- <PR编号>`。入口核对仓库、候选、最新主线、CI 检查和对应证据，并以准确 head 合并。主线 CI 核对真正的合并结果。需要本地核对时，用 `npm run verify:main -- --base <合并前的准确主线提交>`。随后按 [5274 交接](../README.md#业务任务统一验收5274) 与 [任务环境清理](task-completion-cleanup.md) 完成运行、数据绑定和资源交接。

## 证据规则

每项结果绑定标准和规则内容、执行命令、用例范围、源码和测试、相关依赖与环境、原始日志、候选及目标主线。成功证据按检查的相关输入复用。未运行的必测项、失败、缺失或损坏的日志均阻止签发完整交付记录。失败和中断记录保留，重新运行时从仍然有效的检查接续。

本机结果保存在 Git 公共目录的 `zdm-quality/v1.1/`，临时 Worktree 回收后仍可追溯。记录有本机完整性签名，管理本机账号者也管理签名密钥。CI 在独立工作环境内验证；只从 GitHub API 确认的本仓成功 PR 运行获取归档，并核对父提交、合并树、验证计划、环境和原始结果。可变数据库依赖、无法确认的浏览器条件或安装内容使相关结果需要实跑。运行身份、共享数据绑定及交接健康另作现场检查。

分级工具变化由主线已发布规则和基准契约校验。首次接入使用事先单独提交的黑盒契约；后续更新从目标主线读取规则。GitHub 检查名为 `V1.1 quality gate`。远端强制程度以目标分支规则的实际设置为准，本地完整性签名的信任边界是本机账号。
