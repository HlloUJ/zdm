# 任务环境清理

适用于装点猫管理后台收到「任务完成」或「今天工作完成」的当前任务。结项开始时，在已核实并同步 `origin/main` 的本仓库中运行 `git show refs/remotes/origin/main:docs/task-completion-cleanup.md`。旧分支直接读取该版本，无需切换或合并其工作区。先盘点并保护唯一资料，再做可能移除资源的交接。主线交付、本地同步和运行交接均验证通过后，回收清单中的退役资源。开发中、暂停、待验收、返工中的任务和其他历史任务不纳入本次清理。

涉及 [5274 统一验收](../README.md#业务任务统一验收5274) 时，按现有交接入口同步 5274，核实其健康、已交付版本退出组合且其他待验收版本仍在。5274 的固定工作目录、Compose 资源、验收库、媒体、退出账本和必要的迁移备份属于共享环境。如果这次 `sync` 会重建服务，先完成下文的容器核对和资料保全，再调用交接入口。

## 通知总协调登记待交付任务

用户本人向本项目子任务下达「任务完成」时，子任务按原流程冻结该时点的业务快照，在原任务记录中将本次请求记为「待通知」，并在创建 PR 前发送。若 PR 已存在，也在收到指令时通知。用来源对话 ID 和原指令所在轮次识别同一次请求，已通知的请求沿用原回执。引用口令、讨论流程和其他对话转述的消息均不触发。

1. **核实收件人。** 使用用户最近一次有效任命或交接所指定的总协调对话 ID。需要定位时，用 `list_threads` 按完整标题 `^总协调[0-9]{4}$` 查找，四位数字表示有效月日（MMDD），例如「总协调1120」。用 `read_thread` 核对用户的指定记录。同一对话改名沿用原 ID，新对话接任后使用新 ID。多个标题匹配时，只向已核实的在任者发送。
2. **发送交付请求。** 按用户本人对本项目的通知授权，使用 `send_message_to_thread` 向在任对话发送任务名称、来源对话 ID 和原指令所在轮次，请总协调登记为「待交付」并跟踪到该任务版本进入远端 `main`。
3. **核对发送结果。** 收到发送成功回执后，在同一记录记为「已通知」。收件人或授权无法核实、发送失败时保留「待通知」及原因，在任务继续或恢复时补发。发送结果不明时，先读回目标对话，按来源对话和原指令核对，同一请求只登记一次。通知进度不阻塞子任务的既有交付。

## 创建工作区外资产时登记

在当前任务对话或已有私有交接记录中登记，记录放在计划回收的资源之外。创建外部目录、独立 Git 副本、临时导出件或 PR 说明文件时，记下准确路径、用途和所属任务。同一专属临时目录中的文件可按目录登记。创建 Docker 资源后记下实际 Docker 上下文或守护进程、Compose 项目（如有）、资源类型及容器 ID、镜像 ID 或卷名。工具已记录的信息可直接引用。资产迁移、移交或提前回收时更新同一条记录。只记录定位信息，凭证和文件内容留在各自的受保护位置。

### 自动登记和回收

在登记的独立任务 Worktree 通过 `npm run task:timing -- exec 023 -- npm run env:init -- 5323 8323` 创建环境，端口和编号替换为该任务实际值。每次 `exec`、`measure` 将子进程的系统临时目录与 `ZDM_TASK_TMPDIR` 指向本任务专用目录。PR 文本、导出件和可丢弃的测试输出放在该目录；需要留档的原始结果直接写到工作区外已有的任务记录。工具会绑定该任务初次生成的随机 Compose 项目及 Docker 引擎。在旧分支执行时可用已同步主工作区的 `dev/task-timing.mjs` 与 `dev/init-env.mjs` 绝对路径，以任务 Worktree 为当前目录调用。已有环境沿原登记核对，不追认同名资源。

需要指定外部文件位置时，在写文件前运行 `task:timing -- temp-file 023 /真实绝对路径/文件`（以上及下列子命令均从 `npm run` 调用）。它排他创建新文件。可丢弃的临时测试卷用 `task:timing -- test-volume 023 用途` 创建，使用返回的唯一卷名。需要保全的文件先复制至该任务记录，再用 `resource-copy 023 '{"path":"原文件绝对路径","backup":"任务记录中副本的绝对路径"}'` 核对独立副本及摘要。已创建的其他外部资产继续按上文登记。多个活跃任务共用的工作目录、已有文件和已有数据库不会因任务编号匹配就获得删除授权。

交接后完成忽略项盘点和必要保全，移除已交付的专属 Worktree。在已同步的主工作区运行原结项命令 `mark 023 '{"stage":"closed","at":"实际结项时间（含时区）","ref":"实际交付凭据"}'`。工具核对任务 PR 候选（或仍保留的本地任务分支）已合入主线、5274 的实际提交和剩余任务、工作区释放情况，然后按登记逐项回收。无 PR 的任务在执行结项命令前保留本地分支作证明。

任务卷先查所有容器。退役容器仅在已退出、可写层无独有改动且日志已保全时移除。任务 Maven 卷只读逐文件核对常驻 Maven 卷，将不同的文件按 SHA-256 单份保全到 Git 公共目录的 `zdm-tasks/maven-objects`；该任务的 `maven-卷名.json` 记录恢复路径。临时数据库须明确使用任务分配的临时卷。Compose 中的业务数据库、媒体、退出账本和有保留标志的卷继续保留。5274 在交接锁内复用相同安装输入的前端依赖，保留当前版本、回滚版本、待验收版本和仍有引用的依赖。

用 `resources 023` 查看每次回收的时间、文件系统可用空间、移除、保留及待处理清单，记录位于 Git 公共目录的 `zdm-tasks/023/resources-v1.json`。被占用、身份已变或暂时无法核验的项目逐项留存原因。下一次任务结项或 5274 成功交接会重试，也可手动运行 `retry-cleanup 023`。完整环节前后的宿主空间仍按下文采样，不能把多个重试区间重复相加。

## 盘点当前任务的资产

1. 从实际任务 Worktree、任务记录和运行配置取得可验证的归属证据。沿这些记录查找仓库外的任务临时目录、归档、导出件、测试副本和 Docker 绑定挂载。旧分支缺少资产登记时，只沿本任务已有线索补录。逐项记录准确路径或资源标识、归属及使用方、删除或保留决定和依据。目录名、时间、端口或资源名称前缀只用于定位。
2. 在任务 Worktree 根目录检查已修改和未跟踪内容。另用 `git ls-files --others --ignored --exclude-standard --directory -z` 盘点 Git 忽略项，包括 `.private/`、`.env` 和本地测试数据。对将整体移除的目录，去掉 `--directory` 并将路径限定到该目录，核对其中独有的文件。`git status` 干净也要检查忽略项。
3. 将本轮拟删除的目录、文件、Docker 资源和交接会替换的旧容器合成一份清单。需要保留的内容至少有一份能在**整份清单移除后**独立恢复。核实符号链接、父目录和挂载指向的实际存储，检查副本及恢复所需的配置是否也将被移除。已交付源码核对远端提交，普通文件可比对内容或已有校验值，数据备份核对对应数据及可用的恢复依据。外部链接指回待删除目录、两份文件均在清单内，或仅能证明备份可读时，把原件及其依赖的载体从删除范围移出，记明保留位置。
4. 把可回收的任务专属依赖副本、构建产物、临时文件、测试副本和已核对的重复资料列入清单。共享依赖缓存、必要备份、有效回滚资料和归属不明的资产保留。交接验证通过，且目录中的内容都可删除或已妥善保全后，才整体移除目录或 Worktree。

## 核对并回收独占 Docker 资源

任何可能移除或重建容器的操作（含交接脚本间接执行的 `down`、`up` 重建）开始前，在准确的 Docker 上下文中确认本次会涉及哪些容器。可从 `.env` 取 `COMPOSE_PROJECT_NAME` 定位，再结合实际启动参数、Compose 项目和工作目录标签，按容器 ID 核对运行中和已停止的容器及其使用方。可用 `docker diff` 查看可写层改动的路径，另查卷和绑定目录。确认独有资料在整份待删除清单之外可恢复，再执行相应操作。范围不明或有唯一资料尚未保全时，保留原容器和挂载，继续处理独立且已核实的对象。

- **容器**仅回收已核实归属的当前任务退役容器。若交接已将其移除，按该容器 ID 读回移除前的核对与保全记录，避免重复操作。缺少事前记录且容器已消失时，如实报告无法确认其资料是否已保全。
- **镜像**：只移除可重建、明确由该任务独占、且没有其他环境引用的镜像，核对镜像 ID、所有标签和其他环境配置。Compose 中的通用 `mysql` 和 `maven` 镜像按共享依赖处理。
- **卷**：只移除无其他挂载方，且已核实可重建或有可用备份的任务专属临时卷。数据库、媒体和 `store-exit-ledger` 需要分别核对用途及恢复来源。带 `com.zdm.retained-data` 保留标记的卷，以及正式、共享、预览或仍用于回滚的卷都保留。Docker 绑定挂载目录按文件资产规则单独判断。

保留共享资源和无法重建的唯一副本。每次删除前复核准确对象和使用方。优先用普通 Docker 命令处理清单中的具体对象，避免全局 `prune`、批量 `docker compose down -v` 和强制删除。资源变化、仍被占用或无法证明安全时保留该项并记录原因，继续其他可安全清理的项目。

## 实测空间并报告

在第一次移除资源前和最后一次移除后，用 `df -Pk` 对同一组仍存在的宿主机路径采样。若现有运行交接会移除容器，首次采样提前到该步骤之前。至少检查工作区所在文件系统，若任务外部文件或 Docker 本地存储位于其他文件系统，也测量对应文件系统。选择同一挂载上的稳定路径，例如将被删除目录的父目录。记录采样时间、挂载点、清理前后的 `Available` 值和差值，单位为 KiB。同一文件系统的差值只计一次。Docker 报告的对象大小不加到宿主实测差值中。无法定位实际存储或测量失败时，记录具体原因。

清理后核对目标是否移除、保留的原件或备份是否仍可使用，以及受影响的共享环境是否健康。结项结果记录实际移除项、保留项及原因。每个文件系统报告“采样期间宿主机可用空间净变化”（清理后减清理前），包括零值和负值。其他任务的并发读写也会影响这个数。存在必要步骤未完成时，分别报告源码交付、运行交接和环境清理的状态。
